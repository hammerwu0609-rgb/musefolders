## 0. 交接结论先行

曲境不是“自动给所有歌曲分文件夹”的单一工具，而是一套以本地音乐为数据源、以**可解释的音乐地图**为核心、以**用户审查后生成歌单或文件夹**为出口的私人音乐探索系统。它现在的主路径是：

> **选择本地曲库 → 建立逐曲档案与声音画像 → 在多张 Music Map 中找歌 → 把结果加入统一候选歌单 → 试听、排除、排序 → 保存为 M3U8 或复制成文件夹。**

项目已经形成可运行的完整原型，主要完成了：本地曲库扫描、元数据与封面读取、基础声学编码、ACT/BRI 二级编码、MusiCNN 200 维听感画像、听感 Map、主题群岛基础版、流派/语言地图框架、相似歌曲、Song Path、Song Alchemy、候选歌单、审查与导出、全库整理、中英文界面、错误原因与解决办法提示，以及面向未来平台接入的三类接口。

交接后最重要的工作不是继续堆功能，而是按以下顺序补齐产品闭环：

1. **P0：维护版本控制、最终确认项目与模型许可证、轮换已暴露的 API Key。**交接时已建立本地 Git 基线并加入临时的私有仓库 `All Rights Reserved` 声明；公开发布前仍须确认权利人法定名称和全部模型条款。
2. **P0：完成“有声/纯音乐/不确定”自动识别和歌词工程。**它决定主题 Map 的证据链是否成立。
3. **P0：建立流派数据的多来源校验机制。**音频模型只能给候选，不能把模型猜测伪装成确切流派。
4. **P0：完成 5 人无说明可用性测试。**自动化测试通过不等于用户真的会用。
5. **P1：先做 Windows 本地封装，再讨论云端。**当前产品必须读取用户本机任意音乐目录；单纯把 Streamlit 放到服务器后，服务器看不到用户电脑的本地路径。
6. **P1：把可选 LLM 固定为“意图翻译器和解释器”，而不是标签事实源或文件执行器。**

本文所有能力都按四种状态区分：

- **已实现**：代码中存在，已有自动化测试或实际样本证据。
- **实验性**：可运行，但准确率、覆盖率或用户价值尚未充分验证。
- **框架已留**：接口或交互入口已存在，真实外部能力尚未接通。
- **未实现**：只有已确认的产品方案，不应在演示或宣传中说成已完成。

# 第一部分：完整项目说明

## 1. 项目要解决什么问题

### 1.1 用户痛点

音乐平台擅长提供搜索、榜单、推荐和一句话生成歌单，但私人曲库仍存在几类没有被很好解决的问题：

1. **用户看不见自己的曲库结构。**收藏列表通常是时间流或平面清单，用户不知道哪些歌在听感上聚在一起、哪些是孤立曲目，也很难重新发现被遗忘的歌曲。
2. **自然语言推荐通常不可审查。**用户说“明亮、偏快、有人声”，平台可能返回结果，却不一定说明每首歌为什么进入、用了什么证据、哪些条件并未满足。
3. **元数据不可靠。**本地文件可能缺少歌手、专辑、年份或流派，也可能整批写着同一个错误流派。当前 95 首样本的 `Genre` 全部为 `Blues`，就是不能直接信任元数据的实例。
4. **本地曲库与云端收藏之间存在权限断层。**能列出曲目不等于能取得音频，能取得音频也不等于能写歌单；只拿到查询 Key 不能自动获得三种权限。
5. **全库一次性整理风险高、实用性有限。**用户更多时候只想临时找一批符合当下目的的歌，而不是每次把全部文件永久重排。
6. **音乐分析工具常把专业内部结果直接丢给用户。**高维向量、UMAP、余弦相似度、置信度等术语如果没有可视化和渐进式交互，会增加理解成本。
7. **“未知”经常被系统强行填满。**流派、主题、乐器、人声状态其实都可能证据不足；错误地给出肯定结论，会比保留“待确认”更伤害信任。

### 1.2 业务机会

QQ 音乐等平台已经能够使用大模型按自然语言生成歌单，因此曲境不应和平台在“聊天生成歌单”上正面同质竞争。更有价值的定位是：

- 将私人曲库变成**可浏览、可试听、可解释、可修正**的空间；
- 让用户先看见数据，再决定歌单，而不是要求用户相信一个黑箱答案；
- 以本地合法可读音频为起点，在没有云端 API 时仍能成立；
- 将分析结果与输出平台解耦，未来既可以写本地 M3U8，也可以在取得官方权限后写 QQ 音乐歌单；
- 把地图、趣味星象和分享卡变成社交表达，但不把趣味包装冒充科学人格测验。

### 1.3 核心用户与典型任务

核心用户包括：本地音乐收藏者、歌单重度用户、希望重新发现旧收藏的人、对音乐分析与可视化感兴趣的用户，以及在平台推荐之外希望保留自主判断的人。

三个典型任务是：

1. **探索任务**：“我想看看曲库里偏快、明亮、活跃的歌集中在哪里，并找到一首意外喜欢的歌。”
2. **定制任务**：“我想从所有歌曲中筛出若干首符合特定元数据、声学标签或主题的歌，试听后生成一个歌单。”
3. **整理任务**：“我想把已审查的候选歌曲复制进一个文件夹，或按 1—3 个标签分成多个文件夹，但不能改动原文件。”

## 2. 产品定位与核心方案

### 2.1 一句话定位

**曲境是一款本地优先、可解释、可审查的私人音乐地图与歌单工作台。**

“本地优先”意味着核心地图和整理功能不依赖云端大模型；“可解释”意味着每种标签说明来源和局限；“可审查”意味着系统先提出候选，用户再试听、排除、排序和保存。

### 2.2 北极星体验

主工作流被统一为三个步骤：

1. **找歌**：在听感、主题、流派、语言地图中点击、框选、圈选，或使用条件筛选、相似曲、Song Path、Song Alchemy。
2. **审查**：试听候选、查看基本信息与标签依据、排除不合适曲目、调整顺序、修正主题/乐器/流派。
3. **保存**：下载 M3U8，或经预览与二次确认后复制为单歌单文件夹或多个分类文件夹。

地图或算法得到的结果都先成为“这批发现”，再由用户选择：

- **加入候选**：新结果与原候选合并，按音频内容指纹去重。
- **仅保留交集**：只保留“原候选中同时也属于本次结果”的歌曲，用于逐步收紧范围。
- **新建候选**：用本次结果替换原候选，并清空旧排除状态。

点击单个地图点默认只查看，不暗中修改歌单。这是产品信任的关键。

### 2.3 产品差异点

曲境不宣称“比 QQ 音乐更懂用户”，而强调以下差异：

- 用户可以看见整库分布，不只得到一份结果；
- 声音相似、文字主题、专业流派、演唱语言被拆成不同地图，不混为一个坐标空间；
- 2D 图只用于浏览，高维向量才用于精确相似排序；
- 每个结论都区分“原始元数据、模型估计、标题线索、歌词支持、人工核实”；
- 用户可在保存前试听并逐曲否决；
- 输出是平台无关的歌单草稿，未来可以接本地、QQ 音乐或其他平台。

| 功能 | 状态 | 当前含义与边界 |
| --- | --- | --- |
| 本地目录扫描 | 已实现 | 递归读取 MP3、WAV、FLAC、M4A、OGG、OPUS、AAC；受保护格式明确跳过，不解密 |
| 元数据、封面 | 已实现 | 读取曲名、歌手、专辑、年份、Genre、来源 ID 和内嵌封面；缺失时从文件名保守补全 |

## 4. 技术架构总览

### 4.1 当前运行架构

```text
用户本地音乐目录（只读）
        │
        ├── 文件发现、SHA-256、元数据、封面
        │
        ├── 基础声学分析（librosa / NumPy）
        │       ├── BPM / RMS / 调性 / 频谱特征
        │       ├── ACT / BRI / 一级标签
        │       └── YAMNet 主要声源提示
        │
        ├── 可选声音画像（MusiCNN ONNX / ONNX Runtime）
        │       ├── 200 维向量缓存
        │       ├── 原始空间相似检索、Path、Alchemy
        │       └── UMAP 候选布局 + BPM/BRI 语义轴约束
        │
        ├── 可选文字画像（标题 / 本地歌词 / GTE）
        │       ├── 主题证据与语言识别
        │       ├── 主题相似检索
        │       └── 主题加权分区群岛
        │
        └── CollectionPlan（平台无关逐曲档案与计划）
                 │
                 ├── Streamlit / Plotly / 自定义 SVG 交互
                 ├── PlaylistDraft 统一候选草稿
                 └── 输出适配器
                         ├── 本地 M3U8
                         ├── 本地文件夹复制 + 清单 + 撤销
                         └── 未来 QQ 音乐官方 PlaylistWriter
```

当前所有核心处理在用户本机完成；Streamlit 只是本机 Web 界面，服务监听 `127.0.0.1:8501`，并不代表数据已经上传到云端。

### 4.2 完整技术栈

| 层 | 技术 | 在本项目中的作用 |
| --- | --- | --- |
| 语言与运行时 | Python 3.11（允许 `<3.13`） | 主程序、分析、缓存、导出和测试 |
| 依赖管理 | `uv`、`pyproject.toml`、`uv.lock` | 锁定环境；按 `dev`、`sonic`、`lyrics` 三组可选能力安装 |
| UI | Streamlit 1.64+ | 页面、状态、试听、表格、按钮、筛选和流程组织 |
| 图表 | Plotly 6+ | 听感/分类散点图、点选、框选、圈选、缩放 |
| 主题图组件 | Streamlit HTML/SVG 双向组件 | 点击整个主题区块、保存主题图视野状态 |
| 数值与表格 | NumPy、pandas | 特征、向量、统计、表格 |
| 音频读取与 MIR | librosa、soundfile | 解码、采样、节拍、频谱、HPSS、chroma 等音乐信息检索 |
| 元数据 | TinyTag、Mutagen | 常规元数据、封面、内嵌歌词与多格式标签 |
| 声音模型推理 | ONNX Runtime | 运行 MusiCNN ONNX，得到 200 维声音画像 |
| 主要声源模型 | MediaPipe Audio Tasks + YAMNet TFLite | 音频事件分类后保守归并为主要声源大类 |
| 降维 | UMAP；PCA 兜底 | 把高维向量变成可画的二维候选布局；不用于精确相似度 |
| 文字模型 | `Alibaba-NLP/gte-multilingual-base` + sentence-transformers | 标题/歌词多语语义向量，按固定 revision 加载；默认不自动下载 |
| 语言识别 | fastText `lid.176.ftz` | 从有效歌词识别语言；模型为可选资产 |
| 云端 LLM | DeepSeek OpenAI-compatible Chat Completions | 可选条件编译和单曲主题解释；本地功能不依赖它 |
| 图像 | Pillow | 生成本地星座分享卡 |
| 测试 | pytest、Streamlit AppTest | 单元、接口、交互主路径与安全约束验证 |
| 启动 | PowerShell、CMD | 安装环境、启动本地服务、健康检查和自动打开浏览器 |

通俗解释：MIR（Music Information Retrieval，音乐信息检索）就是用程序从音频里测节奏、频谱、调性等信息；“向量”是把一首歌变成一串可以比较的数字；“降维”是把几百个数字压成二维画出来，但压缩必然损失信息。

### 4.3 核心数据对象

#### `TrackMetadata`

保存曲名、歌手、专辑、原始流派、年份、平台来源曲目 ID 和元数据来源。原始流派只忠实呈现，不自动等同于已核实流派。

#### `AcousticFeatures`

保存逐曲基础声学测量，包括：

- `tempo_bpm`、`tempo_confidence`：速度与节拍证据；
- `rms_dbfs`：数字音频平均电平，作为响度代理；
- `dynamic_range_db`：片段内强弱变化；
- `spectral_centroid_hz`、`spectral_rolloff_hz`、`high_frequency_ratio`：明亮度相关频谱特征；
- `zero_crossing_rate`：波形过零率；
- `percussive_ratio`、`harmonic_ratio`：打击性与谐波性比例；
- `onset_rate`：单位时间起音事件数量；
- `key`、`mode`、`key_confidence`：调性、调式与内部区分度；
- `analyzed_audio_s`：实际分析的音频秒数。

#### `TrackEncoding`

是系统最重要的逐曲档案：把文件身份、SHA-256 内容指纹、元数据、基础声学特征、主要声源、ACT/BRI、标签、流派证据状态、警告和版本号放在一起。平台输出不应直接依赖 UI，而应依赖此对象。

#### `CollectionPlan`

是一份平台无关的曲库分析与分类蓝图。它保存分析 ID、来源目录、逐曲档案、文件夹方案、标签选择、失败和跳过文件。未来 QQ 音乐接入后，仍应让同一份计划驱动新的输出适配器。

#### `PlaylistDraft`

是“地图探索”和“高级档案”共享的候选歌单草稿。它保存顺序、来源操作、排除记录、筛选条件和内容指纹。重扫以后优先按同一文件实例恢复，其次按 SHA-256 找回同一录音；绝不静默替换成另一首歌。

### 4.4 平台能力接口

平台接入被拆成三个独立接口，这是未来接 QQ 音乐时最重要的架构决定：

1. `CatalogReader`：只能列出用户可见曲目及元数据。
2. `AnalyzableAudioProvider`：在有明确授权时提供可被模型读取的真实音频路径。
3. `PlaylistWriter`：把用户已经审查、排序的曲目列表写成平台歌单。

此外还有：

- `SemanticEncoder`：未来可替换或增加 CLAP、平台自有模型等语义编码器；
- `NaturalLanguageRuleCompiler`：把自然语言请求编译成同一套可检查的筛选计划；
- `CloudLibraryClient`：仅为旧 QQ 适配器兼容保留，不应继续把不同权限混在一起。

必须坚持：**目录权限 ≠ 音频权限 ≠ 写歌单权限。**若只拿到 QQ 曲目元数据，就只能展示 catalog；没有音频授权，不能伪造听感向量；没有写权限，不能声称已经创建云端歌单。

## 5. 全系统技术逻辑

### 5.1 曲库发现与文件身份

`service.discover_audio()` 递归扫描来源目录：

- 支持：`.mp3`、`.wav`、`.flac`、`.m4a`、`.ogg`、`.opus`、`.aac`；
- 受保护格式：`.mgg`、`.qmc0`、`.qmc3`、`.qmcflac`、`.kgm`、`.ncm`；
- 受保护文件只记录“受保护格式，不尝试解密”，不绕过 DRM；
- 每个可读文件计算 SHA-256；
- `track_id` 由“内容哈希 + 绝对路径”生成，用来区分同一录音的不同文件实例；
- 内容哈希单独保留，用来跨路径去重、恢复人工修正和候选歌单。

基础分析缓存键包含引擎版本、绝对路径、文件大小和修改时间；读取缓存后仍会重新校验实际 SHA-256，避免源文件被替换后沿用旧分析。

### 5.2 元数据与封面

TinyTag 读取标题、歌手、专辑、Genre、年份和可能的来源 ID；缺少标题/歌手时尝试把 `歌手 - 曲名` 文件名拆开。封面只读取文件内嵌的 JPEG、PNG 或 WebP，转成 data URI 供页面展示，不访问网络、不写回音频。

本地“文件创建时间”只作为下载时间参考。复制、恢复或迁移文件都会改变它，产品不得把它表述为确定的实际下载日期。

### 5.3 基础声学分析

每首歌默认取最多三段、每段 24 秒：前部、中央、末部。每段在 22.05 kHz 单声道下分析，最后对各段数值取中位数，以降低单个 intro、solo 或 outro 的影响。

关键计算包括：

- BPM：使用 onset strength 和 beat tracking；
- 响度代理：RMS 振幅转 dBFS；
- 动态范围：RMS dB 的第 90 百分位减第 10 百分位；
- 频谱重心：能量在频率上的“重心”；
- 频谱滚降：累计到 85% 能量的频率；
- 高频比例：3 kHz 以上能量占 80 Hz 以上宽带能量的比例；
- 过零率：波形穿过零轴的频率；
- HPSS：把信号近似分成谐波和打击成分，得到两者比例；
- 起音密度：每秒检测到的 onset 数；
- 调性/调式：把 chroma 与 Krumhansl-Schmuckler 大/小调轮廓逐一比较，输出主音、major/minor 和候选分离度。

这些都是估计，不是人工乐理鉴定。BPM 可能发生半拍/倍拍误差；RMS dBFS 不是 LUFS；调性模型不能处理所有转调和复杂调式。

### 5.4 ACT 与 BRI

所有输入先按固定物理范围缩放到 0—1，再裁剪，避免同一首歌因为换了曲库而改变分数。

#### ACT（声音活跃度）

```text
ACT = 100 × (
    0.30 × scale(BPM, 60..180)
  + 0.25 × scale(RMS dBFS, -38..-10)
  + 0.25 × scale(打击乐比例, 0..0.5)
  + 0.20 × scale(起音密度, 0.5..6.0)
)
```

ACT 表示声音的运动与力度倾向，不是情绪、躁动人格或兴奋程度的医学/心理学判断。低于 35 为低，35—60 为中，60 及以上为高。

#### BRI（声音明亮度）

```text
BRI = 100 × (
    0.50 × scale(频谱重心, 500..4500 Hz)
  + 0.25 × scale(85% 频谱滚降, 2000..9000 Hz)
  + 0.25 × scale(3 kHz 以上能量比例, 0.01..0.30)
)
```

BRI 描述高频能量与频谱位置的一部分，不等于完整音色。ACT 公式不直接引用 BRI，因此定义上不重复；但真实音乐中活跃编曲可能同时更亮，统计相关不可能被强制为零。当前样本 ACT–BRI 相关系数约 `+0.608`，说明在这批歌中仍明显同向，不能宣称三个视觉维度相互独立。

### 5.5 主要声源

YAMNet 是一个 521 类音频事件分类模型。曲境取歌曲两处 8 秒片段，将相关类别汇总到七个大类：人声、钢琴、吉他、弦乐、管乐、打击乐、合成器。只有当平均证据超过阈值并与第二名拉开差距时才给出模型估计，否则为 `unknown/待确定`。

这不是音乐分轨，也不是演奏人员名单。当前样本只有 7/95 首达到保守门槛，说明此能力只能作为提示。用户可试听后人工修正，修正按内容哈希保存，不改源文件。

### 5.6 MusiCNN 声音画像与相似度

MusiCNN 输入 16 kHz 单声道音频。曲境从歌曲前、中、后三处各取约 8 秒，计算 96 个 mel 频带、187 帧的 log-mel patch，批量送入 ONNX 模型，得到逐 patch 的 200 维输出，取平均并归一化为逐曲声音画像。

缓存键包含：音频内容哈希、模型文件哈希和预处理版本。模型换了、预处理换了或音频变了，缓存不会被错误复用。

模型缺失、ONNX Runtime 缺失、模型加载失败都会显式降级到 13 维基础声学向量；如果模型能加载但所有歌曲推理失败，也降级，并保留失败原因。基础地图不能冒充完整 MusiCNN 地图。

相似歌曲、Song Path、Alchemy 一律在原始高维单位向量中用余弦相似度计算。余弦相似度可通俗理解为“两个数字方向有多接近”；越接近 1，画像方向越像。屏幕上两个点挨得近，只能做浏览提示，不是精确相似度。

### 5.7 听感 Map 的坐标逻辑

听感图固定表达三种范畴：

- 横轴：BPM 趋势，固定量程 60—180 BPM 映射到 0—100；
- 纵轴：BRI 0—100；
- 点颜色：ACT 0—100，由冷蓝向暖橙变化。

若已经建立 MusiCNN 画像，系统可用 UMAP 将 200 维压到二维，再通过正交对齐和小幅残差混合，让显示位置适当保留模型邻域。只有满足两条限制才接受模型调整：

1. BPM 和 BRI 的排序一致度都不能低于 0.85；
2. 二维邻居与原始向量邻居的重合率必须比纯 BPM/BRI 布局更好。

允许的混合权重只有 0.1、0.2、0.3；若没有改善，保持纯语义轴。已有曲目坐标写入投影缓存；新增歌曲时保留旧点，并按旧近邻残差锚定新点，从而避免每次打开地图都“搬家”。

页面支持点选、框选、圈选、1×/2×/4×/8×、缩小和复位。查看倍率不是音乐距离单位。对屏幕上过密点位另提供“重叠歌曲”列表，不能仅依赖用户无限放大。

### 5.8 听感星座

星座只解释当前已经显示的点阵，不参与声音分析，也不能改动任何歌曲点：

1. 先按内容哈希去重；少于 12 首显示“星群种子”；
2. 达到 12 首后，使用全部点位构造整体轮廓；
3. 与十二套固定象征轮廓做允许平移、旋转、等比缩放的相对匹配；
4. 选出十二者中相对最接近的一种，并生成不遮挡交互的浅色连线；
5. 星座固定映射到火、土、风、水元素；人工改选星座后元素随之改变并标明自选；
6. 本地分享卡可包含星座、元素、点阵缩图、依据和日期；是否显示代表歌曲由用户决定。

它必须始终标注为“十二种趣味轮廓中的相对匹配”，不称人格、命盘、运势或“此刻心情”。

### 5.9 主题解析与主题 Map

主题系统与听感系统完全独立：听感相似使用音频向量，主题相似使用文字向量，两张地图的坐标不能直接比较。

#### 歌词来源优先级

1. 用户为单曲手工选择的歌词文件；
2. 音频同目录、同文件名的 `.lrc` 或 `.txt`；
3. MP3/FLAC/OGG/OPUS 等文件内嵌歌词；
4. 指定外部歌词目录中的唯一同名匹配。

出现多个候选、曲库内存在重名文件或不同来源冲突时，状态为“有歧义”，要求人工确认，不能静默猜一个。LRC 时间戳、头部元数据、段落标题会被清理。有效歌词要求至少 40 个内容字符；较短但有信息的片段可作为“部分歌词”。

#### 当前证据融合

- 人工主题修正优先级最高；
- 人工确认纯音乐：只使用标题；
- 有完整歌词且标题有意义：标题权重 0.2、歌词权重 0.8；
- 只有可用的短歌词：标题 0.6、歌词 0.4；
- 标题无意义但歌词可用：歌词 1.0；
- 没有歌词：只允许标题提供线索；
- 标题线索只有一个明确主题词时才自动进入该主题，否则进入“待确认”。

GTE 多语文本模型将标题和歌词变成文字语义向量。长歌词分块，最多取 24 块，每块最多 360 字符，按字符数加权汇总。缓存只保存文字 SHA-256 与向量，不保存明文歌词。

当前主题为：爱情、亲情、友情、回忆、孤独、希望与成长、旅途、欢聚、自然，以及待确认。主题提示向量用于比较，不是概率；完整歌词第一名与第二名的相似分差小于 0.015 时不强行定主主题，部分歌词门槛为 0.035。标题单独使用时不靠未经标定的余弦阈值硬判，而依赖严格关键词。

#### 主题群岛布局

主题 Map 不是逐曲散点，而是不规则、紧凑、互不重叠的区块：

- 主题中心位置固定，编码了爱情—亲情—友情等大致语义邻近；
- 已出现的主题在一个固定自然外轮廓内做加权 Voronoi/power diagram 分区；
- 区块面积随歌曲数平方根增长并设上限，避免大主题吞掉全图；
- 待确认位于左侧独立中性区域，不暗示它与某个主题相近；
- 重扫后位置稳定；横纵方向本身没有独立语义；
- 点整块后展开曲目、试听和“歌词支持/仅标题推测/人工修正”等证据；
- “按主题找相似”使用原始文字向量，不使用屏幕像素距离。

#### 当前纯音乐缺口

系统目前不会自动判别纯音乐。只有用户手工确认后，状态才是 `instrumental`。没有歌词可能意味着纯音乐，也可能意味着歌词缺失、匹配失败、扫描不到或歌曲包含人声但没有文本，不能据此判断。

### 5.10 演唱语言 Map

语言识别只读取清洗后的歌词，不能从歌名、歌手名或文件名推断演唱语言。fastText 按多个歌词片段投票：单段置信度低于 0.55 不计；第一语言总权重低于 65% 时为未知；第二语言达到 25% 时为混合语言。纯音乐由人工确认后单独显示为 instrumental。

### 5.11 流派 Map

逐曲档案始终显示文件内的原始 Genre。但若曲库至少有 5 条流派，且其中 80% 以上完全相同，系统认为可能是批量错误，不把它用于专业流派分类。当前 95 首全部标为 `Blues`，因此流派地图提示数据不足。

流派地图目前只使用人工核实的流派。原因是 J-pop、Electronic、Shoegaze 等专业流派无法只靠 BPM、响度、明亮度准确确证；音频模型未来可以提供候选，但必须标明模型、置信度、分类体系和来源。

### 5.12 探索算法

#### 相似歌曲

以当前曲目原始向量为查询，按余弦相似度排序；先应用用户硬条件，再按音频内容去重，并限制同一歌手数量。锚点本身排除。低于最小相似度的候选不加入。

#### Song Path

用户选择起点和终点。算法在两者单位向量之间构造若干插值目标，用有界 beam search 从真实曲目中找路径；每一步既要接近插值目标，也要与前一首足够接近。曲库不足或路径断开时，明确显示无路径/路径缩短，不塞无关曲目。

#### Song Alchemy

多首“喜欢”歌曲按用户权重求向量中心；“不喜欢”歌曲形成排除锚点，在候选集中按相似度百分位排除最靠近它们的一部分，再按喜欢中心排序。喜欢/不喜欢锚点本身不重复进入结果。

### 5.13 条件筛选与冲突处理

可筛选：标题、歌手、专辑、原始流派、年份、主要声源、调性、响度等级、速度等级、ACT 区间、BRI 区间。

- 同一字段选择多个值：OR/并集，例如“钢琴或弦乐”；
- 不同字段同时使用：AND/交集，例如“钢琴且较快且 ACT 6—9”；
- 一级与二级编码允许同时选，不需要报错，因为它们是不同约束；
- ACT 本身包含 BPM、RMS 等分量，所以组合条件可能变得很窄；
- 结果为零时，不报“逻辑冲突”，而计算“撤掉哪一项能恢复多少首”，让用户放宽条件。

每个筛选选项后的数字是在“其他条件已经生效”的前提下计算，帮助用户预判组合后还剩多少首。

### 5.14 文件输出、安全与撤销

本地输出采用两阶段：

1. `preview()`：计算目标文件夹、文件名、复制动作和播放清单，不写文件；
2. `apply()`：用户确认后再次验证所有源文件仍在曲库内、大小/时间/哈希未变，再复制。

约束包括：

- 输出目录不能是磁盘根目录；
- 输出目录不能与源曲库相同，也不能互为上下级；
- 文件夹名和文件名按 Windows 规则清理；
- 重名目标使用可预测的去重名称；
- 源文件永不移动、不改标签、不覆盖；
- 输出清单记录哈希；
- 撤销只删除本次生成且之后未被用户修改的副本；
- 用户已经改过的副本保留并提示，不为了撤销而破坏用户数据。

M3U8 是 UTF-8 播放清单，保存原音频绝对路径，不复制文件。原文件移动后旧列表会失效。

## 6. 产品与交互逻辑详解

### 6.1 首页与来源选择

侧栏提供语言切换、音乐来源文件夹、系统文件夹选择器、分析档案位置和“分析此文件夹”。默认样本目录为项目同级的 `音乐samples`。浏览按钮通过 Tk 系统对话框选择目录；为避免 Streamlit 已创建控件后修改 session state 的已知错误，选择结果在下一次页面运行前写入。

分析档案必须位于源曲库之外，防止缓存、计划和导出清单被重新扫描成曲库内容。页面明确说明原始音乐只读。

### 6.2 默认“音乐探索”工作区

完成分析后默认进入音乐探索，而不是立即让用户配置几十个标签。页面按“① 找歌 → ② 审查 → ③ 保存”组织：

- 地图与基础操作先显示；
- 模型、精确阈值、诊断信息放在可展开区域；
- 当前候选首数和“去审查”始终可见；
- 右侧曲目详情显示封面、元数据、声学标签、证据和试听；
- 地图点点击只聚焦；区块、框选或算法结果先进入待处理结果；
- 用户明确选择加入、交集或替换后，草稿才变化。

### 6.3 四张地图的职责

1. **听感地图**：回答“听起来接近哪里、节奏/明亮/活跃如何”；核心地图。
2. **主题地图**：回答“标题和歌词大致在谈什么”；文字内容地图。
3. **流派地图**：按已核实的专业流派分组；不是声学自动猜测图。
4. **语言地图**：按歌词中的演唱语言分组；没有歌词时保持未知。

听感与主题是重点；流派与语言作为独立分类视图。主题相似按钮和听感相似按钮名称必须清楚区分。

### 6.4 高级工具工作区

“高级工具：档案与全库整理”保留原产品架构，供需要完整数据和精确控制的用户使用：

- 逐曲表格分为基本信息、基础编码、二级编码；
- 查看封面和试听；
- 手工修正主要声源；
- 组合元数据和编码筛选，送入统一候选；
- 全库勾选 1—3 个标签分文件夹；
- 修改文件夹名和单曲归属；
- 预览、确认、复制、撤销。

全库标签最多三个并非分析能力限制，而是控制组合爆炸：如果每个标签有 3—12 个取值，组合可能生成大量只含 0—1 首歌的文件夹。未来可把硬上限改成“默认最多三个，继续添加时显示预计文件夹数量并要求确认”，但当前实现仍是最多三个。

### 6.5 中英文原则

程序内 UI 文案按 `zh/en` 完整维护；底层标签使用语言无关值，如 `voice`、`major`、`fast`，展示时翻译。切换语言不重新分析音频。用户自己的曲名、歌手、专辑、文件路径和原始流派不翻译。

Streamlit 自带的 Deploy、设置、打印等浏览器框架菜单不属于曲境，无法由应用语言开关控制；当前采用 minimal toolbar 隐藏，而不是用不稳定 CSS 强行替换。

### 6.6 已知错误的人类可读处理

程序对以下已知错误弹出“原因 + 解决办法”：

- 文件夹输入状态冲突；
- 系统文件夹选择器打不开；
- 来源目录不存在；
- 分析档案目录与源曲库重叠；
- 没有支持格式；
- 所有文件解码失败；
- 读写权限或磁盘空间不足；
- 输出目录是磁盘根目录或与曲库重叠；
- 输出位置被普通文件占用；
- 源音乐在分析后发生变化。

未知异常仍写日志并显示通用错误，不应把堆栈直接暴露给普通用户。

## 7. 参考项目与借鉴边界

### 7.1 AudioMuse-AI

AudioMuse 是本项目最重要的产品与算法参照。其公开算法文档描述了 MusiCNN/DCLAP/歌词向量、相似曲、Song Path、Alchemy、Music Map、媒体服务器适配和索引架构。曲境借鉴的是以下**概念与公开技术思路**：

- 用声音画像而不是少数人工标签做相似检索；
- Music Map 只是高维声音空间的二维近似；
- 相似曲、Path、Alchemy 共用向量底座；
- 通过缓存与内容身份避免重复分析；
- 把平台目录和分析数据库做适配映射。

曲境没有照搬 AudioMuse 的应用源码。差异包括：

- AudioMuse 面向 Navidrome/Jellyfin/Plex 等媒体服务器；曲境首版直接扫描普通本地文件夹；
- AudioMuse 的典型 2D Map 更强调 UMAP 声音邻域；曲境为可解释性固定 BPM/BRI 轴，只允许少量模型残差；
- 曲境把地图点选、证据查看、试听、候选审查和本地文件输出串成主流程；
- 曲境的主题总览是可点击的语义区块，不是把文字向量直接画成逐曲散点；
- 曲境严格区分元数据、模型估计和人工核实。

AudioMuse 应用代码采用 AGPLv3。任何直接复制、改写或紧密派生其源码的行为都可能触发相应开源义务；继续开发应坚持 clean-room：只依据公开论文、文档、接口行为和独立测试实现。参考：[AudioMuse 算法文档](https://github.com/NeptuneHub/AudioMuse-AI/blob/main/docs/ALGORITHM.md)、[AudioMuse 许可证](https://github.com/NeptuneHub/AudioMuse-AI/blob/main/LICENSE)。

### 7.2 MusiCNN

曲境随项目提供 `models/musicnn_embedding.onnx`，来自 AudioMuse 的模型发布，但上游是 Music Technology Group / Jordi Pons 的 musicnn。musicnn 使用面向音乐设计的卷积网络从 log-mel 频谱中提取标签或中间画像。曲境使用其 200 维输出作为声音相似底座，自行实现片段采样、缓存、布局、检索和交互。上游为 ISC 许可，分发时必须保留版权和许可通知。参考：[musicnn 项目](https://github.com/jordipons/musicnn)、[ISC 许可证](https://github.com/jordipons/musicnn/blob/master/LICENSE.md)。

### 7.3 YAMNet

YAMNet 是 Google/TensorFlow 基于 AudioSet 的 521 类音频事件模型。曲境不直接把 521 个标签全部展示，而只选择音乐相关类别并保守汇总成主要声源大类。YAMNet 更擅长通用事件检测，不是专门的“主乐器鉴定器”，所以覆盖率低是预期风险。参考：[YAMNet 官方说明](https://github.com/tensorflow/models/blob/master/research/audioset/yamnet/README.md)。

### 7.4 GTE 多语文字模型与 fastText

`Alibaba-NLP/gte-multilingual-base` 用于标题/歌词语义向量，支持多语言，当前代码固定到具体 revision 并要求显式同意下载与执行 remote code。模型卡标注 Apache-2.0，但发行前仍应保存模型卡、revision 和许可证快照。参考：[GTE 模型卡](https://huggingface.co/Alibaba-NLP/gte-multilingual-base)。

fastText `lid.176.ftz` 用于歌词语言识别，官方标注支持 176 种语言、模型许可为 CC BY-SA 3.0。当前文件不应默认随程序分发，除非已经完成署名与相同方式共享义务。参考：[fastText 语言识别说明](https://fasttext.cc/docs/en/language-identification)。

### 7.5 未来可参考但尚未接入的模型/数据源

- Essentia 提供基于 MusiCNN 画像的 voice/instrumental 分类头，可作为纯音乐识别候选；其 MTG 模型统一标注 CC BY-NC-SA 4.0，商业或比赛后产品化前需要取得专有许可或换用兼容模型。参考：[Essentia 模型目录](https://essentia.upf.edu/models.html)。
- Essentia Discogs400 等模型可提供细粒度流派候选，但 400 类体系、训练偏差和非商业模型许可都需要单独评估。
- MusicBrainz API 可按录音、发行、ISRC 等实体返回 genres/tags；当前公共服务要求有意义的 User-Agent，并通常限制为平均每秒 1 次，商业使用另有计划。参考：[MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API)。

首次启动如没有 `.venv`，启动器会调用 `setup.ps1`。命令行方式：

## 9. 分析本地曲库

1. 在左侧选择 CN/EN。
2. 在“音乐来源文件夹”输入完整路径，或点“浏览文件夹”。
3. 展开“分析档案保存位置”，确认它不在源音乐目录内部。默认是项目的 `artifacts`。
4. 点击“分析此文件夹”。
5. 进度条显示正在处理的文件名。基础分析首次可能较慢；重复扫描会使用缓存。

分析只读源文件。若有失败，在 `artifacts/collection_plan.json`、`evidence.json` 和页面警告中查看。

## 10. 使用音乐探索主流程

### 10.1 第一步：找歌

#### 听感地图

1. 默认会先显示基础声学地图；状态会明确标注。
2. 如需完整声音画像，点击“建立模型听感地图”。
3. 读图：越向右 BPM 趋势越快；越向上 BRI 越明亮；越偏橙 ACT 越活跃，越偏蓝越平缓。
4. 点击一个点：只查看该歌曲，右侧显示详情和试听。
5. 框选或圈选：形成一批待处理歌曲。
6. 点 `1×/2×/4×/8×` 或图表缩放按钮查看密集区域；需要回到整体时点复位。
7. 两首歌几乎重叠时，展开“重叠歌曲”列表逐首选择。
8. 星座显示可单独开关；它只作装饰解释。

#### 主题地图

1. 点击主题区块，不必精确点击某个小点。
2. 查看区块曲目数、曲目列表和证据来源。
3. 试听单曲；标题或歌词判断不准确时，人工修正主题。
4. 选择区块内全部或部分歌曲形成待处理结果。
5. 当前样本无歌词时，大多数歌曲会在“待确认”；这是正常的诚实状态。

#### 流派与语言地图

- 流派地图只显示人工核实的流派；若提示数据不足，需要逐曲核实或先完成流派数据工程。
- 语言地图需要有效歌词和本地 fastText 模型；无歌词时保持未知，不能用标题语言代替。

#### 相似歌曲、Path、Alchemy 和条件筛选

- 相似歌曲：先选中一首歌，再点“按听感找相似”。
- Song Path：选择不同的起点与终点，设置长度，生成渐变候选。
- Alchemy：选择若干喜欢/不喜欢的锚点与权重，生成混合结果。
- 条件筛选：选择元数据、主要声源、调性、速度、响度和 ACT/BRI 范围。
- 一句话助手：仅在已经配置新 DeepSeek Key、理解外发内容并勾选同意时使用；先检查模型转换出的条件，再应用。

#### 把结果并入候选

任何地图选择或算法结果都不会立刻覆盖歌单。根据目标选择：

- 加入候选：保留原歌单并追加；
- 仅保留交集：在原歌单内继续收紧；
- 新建候选：放弃原候选，用本次结果重新开始。

### 10.2 第二步：审查

1. 点击“去审查”。
2. 逐曲试听；检查曲名、歌手、专辑、标签和加入来源。
3. 排除不合适曲目。排除不会删除源文件。
4. 用上移/下移调整播放顺序。
5. 若重扫后有歌曲找不到，先处理醒目的缺失提示；系统不会用其他录音偷偷替换。
6. 确认最终首数后进入保存。

### 10.3 第三步：保存

1. 输入歌单名称；非法 Windows 字符会被清理。
2. 选择一种输出：
   - 下载 M3U8：不复制歌曲，只保存原文件绝对路径；
   - 复制到一个歌单文件夹；
   - 勾选 1—3 个标签，把当前候选分成多个文件夹。
3. 使用复制功能时选择与源曲库完全分离的输出目录。
4. 查看预览：源文件、目标文件、文件夹数和曲目数。
5. 勾选确认后执行。
6. 如需撤销，使用本次清单执行撤销；已经被用户修改的副本不会删除。

## 11. 使用高级档案与全库整理

1. 打开“高级工具：档案与全库整理”。
2. 在逐曲档案表查看：
   - 基本信息：封面、曲名、歌手、专辑、发行时间、原始流派、文件创建时间；
   - 基础编码：主要声源、调性、调式、RMS dBFS、BPM；
   - 二级编码：ACT、BRI。
3. 选择一首歌查看大封面、完整详情并试听。
4. 需要时人工修正主要声源并保存。
5. 在按需筛选中组合条件；选项括号内数字表示在其他条件下仍可命中的数量。
6. 零结果时，按页面建议撤销最近条件或放宽能恢复曲目的条件。
7. 将筛选结果送入当前候选，继续走“审查 → 保存”。
8. 若确实要整理全库，进入全库整理，选择最多三个标签，预览预计文件夹数量，确认后再生成方案。
9. 可修改文件夹名或修正单曲归属；保存修改后重新检查复制预览。

## 12. 常见问题排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `127.0.0.1:8501` 打不开 | 本地服务未启动、启动窗口已关闭或端口被占用 | 重新双击启动；保持窗口；关闭旧 Streamlit/Python 进程后再开 |
| 选择文件夹后出现 session state 错误 | Streamlit 控件创建后被旧代码直接修改 | 刷新后重选；当前代码已使用 pending state 修复，若复现记录操作顺序 |
| 扫描不到歌曲 | 格式不支持、受保护或选错目录 | 先用普通 MP3/WAV 小目录验证；查看跳过列表 |
| 全部分析失败 | 解码器、权限或文件损坏 | 检查能否在播放器打开；查看 failures；尝试单首 MP3 |
| 速度非常慢 | 首次基础分析需要解码三段；模型图还需单独计算画像 | 等待首次建立；后续应命中缓存；不要边分析边修改源文件 |
| 模型地图仍是基础图 | ONNX 模型或 onnxruntime 缺失/加载失败 | 检查 `models/musicnn_embedding.onnx` 与 sonic 依赖，查看 fallback reason |
| 主题图大多待确认 | 没有歌词、标题歧义或文字模型未启用 | 这是当前样本真实状态；补 LRC/TXT、启用模型或人工确认 |
| 语言都是未知 | 无歌词或 fastText 模型/依赖缺失 | 放置 `models/lid.176.ftz` 并安装 lyrics extra |
| 流派只有 Blues/地图不可用 | 文件元数据疑似整批错误 | 不要强行使用；完成外部数据匹配或人工核实 |
| 乐器多数待确定 | YAMNet 证据门槛保守且不是专用主乐器模型 | 试听后人工修正；后续更换模型，不要降低阈值制造假精度 |
| M3U8 播放失败 | 原音频移动或播放器不支持绝对路径 | 重新生成或使用复制文件夹输出 |
| 复制失败 | 输出与源目录重叠、无权限、重名或源文件已变化 | 按弹窗解决；重新分析并重新预览 |

现有图文版说明另见 `docs/使用手册.md` 和 `docs/曲境使用手册.docx`。

## 16. 数据工程一：主题 Map 与纯音乐自动识别

### 16.1 目标逻辑

应延续已经确定的规则：

- **自动判定为纯音乐**：只用标题解析主题；
- **自动判定为非纯音乐**：标题 + 歌词融合，完整歌词以歌词为主；
- **不确定**：如果有歌词仍可按“有歌词证据”分析主题，但人声状态保持不确定；如果无歌词则标题线索或待确认；
- **人工修正永远优先**，并按内容哈希跨重扫保存。

必须输出三态，而不是二元硬判：`voiced`、`instrumental`、`uncertain`。同时单独保留歌词状态：`valid/short/missing/ambiguous`。例如“有人声但没找到歌词”应是 `voiced + missing`，绝不能合并成 instrumental。

### 16.2 推荐技术路线

#### 第一层：复用 MusiCNN patch 的人声/纯音乐分类头

优先研究与当前 200 维 MusiCNN patch 兼容的 voice/instrumental 分类头。不要只输入整首平均向量，因为短暂或稀疏人声可能在平均中消失。应保留前/中/后三处各 patch 的输出，逐 patch 推理，再汇总：

- 人声证据高且覆盖足够 → voiced；
- 多段均稳定为 instrumental → instrumental；
- 分段矛盾、置信度低或只出现极短人声 → uncertain。

如果使用 Essentia 模型，先解决 CC BY-NC-SA 4.0 与产品化冲突；比赛演示可用于非商业研发验证，但公开商业发行前必须换许可或获得授权。

#### 第二层：自适应补采样

当前声音画像只取三段。如果三段都没有检测到人声，但曲长较长，不应立即判纯音乐；在三段之间增加 2—4 个补充片段。只有补采样仍稳定无声乐证据才提高 instrumental 置信度。

#### 第三层：YAMNet 作为辅助证据

复用当前 YAMNet 的 Singing、Choir、Rapping、Humming 等类别。它可以提高 voiced 证据，但不能单独证明“无这些标签就是纯音乐”。将其作为加分项或冲突检测项。

#### 第四层：仅对不确定曲目做分离/转写兜底

如果成本允许，对 uncertain 子集使用人声分离模型（例如 Demucs）估计 vocal stem 能量，并可用 VAD/Whisper 检查是否存在持续可辨语音。注意：

- VAD/Whisper 识别不到文字，不等于没有人声；吟唱、哼唱、合唱、失真或外语都可能转写失败；
- 分离模型只处理 uncertain，避免整库速度和安装体积失控；
- 分离后的 vocal 能量也可能包含串音，仍需阈值与人工抽查。

### 16.3 数据结构建议

在 `TrackEncoding` 或独立结果中新增：

```text
vocal_status: voiced | instrumental | uncertain
vocal_score: 0..1
vocal_source: manual | musicnn_head | musicnn+yamnet | separation_fallback
vocal_coverage: 被判为有人声的采样片段比例
vocal_model_version
vocal_reasons[]
```

主题引擎接收 `vocal_status`，但不根据它修改音频标签。歌词与人声两条证据链分别缓存和版本化。

### 16.4 训练/验收集

不能只用当前未知标签曲库评估。至少人工标注 150—300 首，覆盖：

- 纯器乐；
- 正常主唱；
- 很晚才进人声；
- 很短 vocal sample；
- 哼唱、合唱、说唱；
- 现场版、背景对白；
- 音色像人声的合成器；
- 伴奏版、卡拉 OK、remix。

验收优先控制“把有人声误判成纯音乐”的错误，因为它会导致主题系统忽略歌词。建议目标：instrumental 精确率优先达到 95% 以上；覆盖率可以先低。所有阈值、模型版本和混淆矩阵留档。

### 16.5 歌词工程

现有本地解析器已经完成基础能力，接下来需要补“获得歌词”和“真实数据验收”：

1. 扩充真实 `.lrc/.txt` 样本，并保存合法来源说明；
2. 支持用户拖入/选择歌词目录和逐曲纠错；
3. 设计曲名、歌手、时长的多字段匹配，但任何非唯一匹配都必须人工确认；
4. 若接平台歌词 API，必须使用官方授权，并保存平台曲目 ID 与歌词版本；
5. 不在缓存中保存明文歌词，除非产品明确说明存储、删除与加密策略；
6. 云端 LLM 默认只发送用户可见的有限节选，逐曲同意，不后台批量上传；
7. 增加歌词更新后只重算文字画像、不重算音频的回归测试。

## 17. 数据工程二：专业流派解析

### 17.1 问题定义

专业流派不是 BPM、响度或频谱的简单函数。一个模型可以说“更像 Electronic”，但不能把它无条件写成确切 Genre。元数据也可能缺失、过粗、批量错误或使用不同体系。

### 17.2 推荐证据分层

每首歌保存多条候选，而不是一个不可追溯字符串：

| 层级 | 来源 | 可信含义 |
| --- | --- | --- |
| A | 用户人工核实 | 产品内最高优先级，可用于流派地图和文件夹 |
| B | 官方平台/发行数据 | 有平台 ID、ISRC 或明确录音匹配时，作为高可信外部元数据 |
| C | MusicBrainz/Discogs 等目录 | 保留实体 ID、标签票数、来源和时间；需做同名消歧 |
| D | 文件内嵌 Genre | 原样展示，但需检测缺失、常量、过粗与异常 |
| E | 音频模型候选 | 概率/排序提示，不能自动升级为已核实 |
| F | LLM 文本推测 | 只能解释已有证据，不能凭歌名生成确切流派 |

建议新增：`genre_candidates[]`，每条包含 `label`、`taxonomy`、`source`、`source_id`、`confidence`、`status`、`model_version`、`retrieved_at`。最终 `verified_genre` 只能来自 A，或在产品规则明确后由可靠的 B 自动采纳。

### 17.3 获取流程

1. 先读取原始元数据并运行库级质量检测；
2. 优先使用已有 QQ 曲目 ID、MusicBrainz Recording ID、ISRC 等稳定标识；
3. 没有 ID 时，用规范化曲名 + 歌手 + 专辑 + 时长做候选匹配；
4. 结果不唯一时要求用户选择；
5. 拉取外部 genres/tags，映射到内部受控词表，并保存原始值；
6. 音频模型只为仍缺失的曲目给 Top-K 候选；
7. 用户在试听和来源信息旁确认；
8. 只有核实结果进入流派 Map。

### 17.4 流派词表

建立版本化层级词表，例如：大类 `Electronic` 下有 `House/Techno/Ambient`，但同时保留平台原词。不要过早把所有相邻流派强行折叠。UI 默认展示用户能理解的层级，专业层级按需展开。

### 17.5 模型评估

可比较 Essentia Discogs400、MTG-Jamendo genre 或其他有清晰许可证和标签表的模型。评估必须报告：Top-1、Top-3、按大类/细类的混淆、未知拒绝率、中文/J-pop/古典/游戏音乐等本地曲库偏差。没有达到阈值就只显示候选，不落确切标签。

## 18. 交互工程：LLM、简化与 UI

### 18.1 LLM 的正确角色

LLM 只做三类工作：

1. **条件编译**：把“想找偏快、明亮、有人声的歌”转成可见筛选项；
2. **证据解释**：把 ACT/BRI、主题证据等翻译成普通语言；
3. **操作导航**：告诉用户下一步该点哪里，但不代替确认。

LLM 不得：

- 直接写文件或创建云端歌单；
- 把未知流派补成确定值；
- 不经同意上传音频、歌词、曲名、路径或完整曲库；
- 隐藏无法表达的用户条件；
- 绕过本地校验和候选审查。

当前 `filter_assistant.py` 已做到只发送用户输入的 500 字以内描述，并在本地校验返回字段；`theme_assistant.py` 已做到逐曲、预览节选、显式同意。后续要补：成本显示、每用户限额、熔断、重试、超时、服务状态、请求审计（不记内容）和供应商可替换接口。

截至交接日，DeepSeek 官方接口仍支持 `https://api.deepseek.com/chat/completions` 和 `deepseek-flash`。模型名与价格会变，必须通过配置而非硬编码发布，并在每次提交前核对官方文档。

### 18.2 星座交互收敛：只保留自动识别

下一版建议**删除“用户手工改选星座”的功能，只呈现系统根据当前完整听感点阵自动识别出的星座**。理由如下：

1. 星座的产品价值来自“系统如何解释我的音乐分布”这一意外发现；如果用户可以任意选择，结果会退化为普通装饰主题，削弱分析链条。
2. 手工改选会同时改变四元素，容易让用户误以为产品在提供人格定制或占星选择，而不是解释既有点阵。
3. 自动结果更适合形成稳定、可比较、可分享的曲库快照；同一分析版本和同一点阵应得到同一星座。
4. 交互更简单：只需“显示/隐藏星座轮廓”和“查看识别依据”，不再需要十二星座选择器。

实施时保留星座图层的开关，因为关闭装饰有助于密集点选；删除的只是“改成另一星座”的选择器。侧栏显示：自动识别星座、派生元素、匹配依据、生成日期和“趣味轮廓，非人格/运势判断”的固定说明。若点位少于 12 首，仍显示“星群种子”，不允许用户绕过门槛手工指定。

现有 `astrology.build_zodiac()` 已具备确定性的自动匹配；需要删除 `manual_sign`/override 的 UI 入口和分享卡“自选”状态，并增加回归测试：同一点阵多次运行结果一致，关闭图层或切换语言不改变自动结果，自动星座及元素不会反向修改歌曲坐标、标签或候选歌单。

### 18.3 操作简化原则

功能不删，但采用渐进式呈现：

- 首屏只保留来源、分析、地图、试听、加入候选；
- 模型版本、置信度和诊断放入“为什么/高级信息”；
- 对每个地图只保留一个主要行动按钮；
- 候选、审查、保存使用固定底部栏或步骤条；
- 每次操作都先显示影响首数；
- 空结果提供一键撤销最近条件；
- 把“加入/交集/新建”的说明放在首次使用时的短提示中；
- 专业术语旁提供一句话解释，不用长篇弹窗阻断操作；
- 地图默认记住缩放和聚焦，切语言不重置；
- 对用户修正提供“撤销”和来源状态变化，而不只显示保存成功。

### 18.4 UI 视觉

建议建立小型设计系统：8px 间距网格、统一按钮层级、卡片圆角、可访问对比度、固定 ACT 冷暖色标、主题色不与 ACT 冲突。地图、候选托盘和曲目详情应在 1366×768 下不需要长距离滚动。前端成熟后再考虑从 Streamlit 迁移到 React/Tauri；比赛前不应为换框架牺牲稳定性。

### 18.5 软件名

“曲境”与地图、情境、音乐空间一致，中文识别度较好；英文 `MuseFolders` 仍残留早期“文件夹整理”定位，建议统一为 `Qujing`、`MusicScape` 或新的可注册英文品牌前先查重。改名必须同步：包名、窗口标题、启动器、缓存目录、分享卡、文档、域名、商标检索，不要只改首页标题。

## 19. 提交工程：版本控制、封装、服务器与上云

### 19.1 先建立工程基线

交接时已经在项目目录建立 `.git`，并加入临时 `All Rights Reserved` 的 `LICENSE`，用于私有仓库阶段阻止未经授权的复制和分发。它不是公开发行许可证；权利人仍以“曲境项目团队”占位。接手后应立即：

1. 清理不应提交的音乐样本、API Key、用户歌词、缓存、虚拟环境和临时输出；
2. 建立 `.gitignore`；
3. 核对“handoff baseline”提交及私有远端，启用分支保护；
4. 明确团队成员、赛事规则和劳动成果约定下的代码/设计/文档权属；
5. 公开前决定曲境源码许可证，或由全部权利人确认继续保持闭源；
6. 建立 `THIRD_PARTY_NOTICES.md` 与模型资产清单；
7. 使用 CI 在干净环境运行 108 项测试和打包烟雾测试。

### 19.2 推荐封装路线

比赛近期推荐“本地桌面封装”，不是先买服务器：

#### 方案 A：Windows 本地便携版/安装包（近期推荐）

- 用 PyInstaller 或 Nuitka 打包 Python、Streamlit、ONNX Runtime、MediaPipe 和模型；
- 启动一个仅监听 `127.0.0.1` 的本地服务并自动打开浏览器；
- 模型与运行库放在固定资源目录；用户数据放到 `%LOCALAPPDATA%\曲境`；
- 提供安装、升级、卸载、日志目录和崩溃恢复；
- 保留源码开发模式，日常改代码不需要每次重新打包；只在里程碑构建安装包。

验收：一台未安装 Python/uv 的干净 Windows 机器能在 5 分钟内安装、选择中文路径音乐目录、分析 10 首、试听、导出、关闭后再次启动并命中缓存。

#### 方案 B：云界面 + 本地代理（中期推荐）

云端负责账号、配置、分享和平台 API；本地代理负责读取音频、模型推理、缓存和文件复制。两者通过带身份认证的任务协议通信，只上传用户明确选择的特征/结果。这样既保留本地目录访问，又能统一更新 UI。

#### 方案 C：全云上传（只适合用户明确上传）

用户把音频上传服务器后分析。需要解决大文件、版权、带宽、存储成本、删除、隔离和隐私，不适合默认扫描私人本地曲库。

### 19.3 为什么“把当前 Streamlit 上云”不等于完成

Streamlit Community Cloud 或普通服务器运行的是服务器自己的文件系统。网页里的 `C:\Music` 对服务器没有意义；服务器不能直接打开访问者电脑的系统文件夹选择器。云版必须改成上传、同步盘、平台授权，或配本地代理。官方文档也说明 Community Cloud 从仓库构建并运行自己的环境，应用需要的本地文件必须存在于部署环境；文件上传还受大小限制。参考：[Streamlit 部署文件组织](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/file-organization)、[文件上传限制](https://docs.streamlit.io/knowledge-base/deploy/increase-file-uploader-limit-streamlit-cloud)。

因此服务器购置顺序应是：先明确部署形态和数据边界，再做容量评估；不是先买机器。

### 19.4 云服务建议拆分

如果进入生产化，可拆为：

- API Gateway：鉴权、限流、版本；
- Catalog Service：用户曲库与平台映射；
- Analysis Worker：CPU/GPU 任务队列；
- Vector Store：声音/文字向量及版本；
- Playlist Service：草稿、审查、写入；
- Object Storage：用户明确上传的临时文件与分享卡；
- Relational DB：用户、授权、状态和审计；
- Local Agent：本地文件与缓存。

首版不必一次性微服务化。可以保留一个模块化后端，但数据对象与接口要维持上述边界。

### 19.5 建议 API 契约

版本化接口可包含：

```text
GET  /v1/catalog/tracks
POST /v1/analysis/audio-jobs
GET  /v1/analysis/audio-jobs/{id}
GET  /v1/maps/sonic
GET  /v1/maps/theme
POST /v1/drafts
PATCH /v1/drafts/{id}
POST /v1/playlists/preview
POST /v1/playlists/commit
POST /v1/platforms/qqmusic/oauth/callback
GET  /v1/platforms/qqmusic/capabilities
```

每次分析结果都带 `engine_version/model_version/taxonomy_version`。写歌单接口必须接收用户确认后的有序曲目 ID，并支持幂等键，避免网络重试生成重复歌单。

# 第五部分：设计、版权、隐私与安全红线

## 20. 产品与算法红线

1. **不修改源音乐。**默认只读；输出只能复制，不能移动、重命名或改写标签。
2. **不知道就显示不知道。**证据不足时必须是待确认/不确定。
3. **不把元数据当真值。**原始 Genre 和模型流派必须显示来源与状态。
4. **不把 2D 距离当精确相似度。**相似排序使用原始向量。
5. **不把 ACT/BRI 当科学人格指标。**它们是工程描述分数。
6. **不把星座当心理学、天文学或运势结论。**只作趣味轮廓和社交分享。
7. **点击查看不等于加入。**所有歌单变化必须有可见动作。
8. **不为了凑满歌单放宽用户硬条件。**无结果就诚实说明。
9. **不把没有歌词当纯音乐。**人声状态与歌词状态严格分离。
10. **不因获得一个 API Key 就假设拥有音频和写入权限。**逐项验证授权。
11. **不自动上传音频、歌词、路径或完整曲库。**任何外发都要最小化、预览和同意。
12. **中英文新增功能必须同时完成。**用户内容不强制翻译。

# 第八部分：术语表

| 术语 | 通俗解释 |
| --- | --- |
| API | 软件之间约定好的调用接口 |
| Adapter/适配器 | 把同一份歌单计划翻译成本地文件操作或某个平台操作的连接层 |
| Embedding/画像/向量 | 用一串数字表示歌曲声音或文字含义，以便计算相似度 |
| MusiCNN | 针对音乐频谱训练的卷积神经网络；本项目用其中间输出做声音画像 |
| ONNX | 让训练好的模型可在不同运行环境推理的通用格式 |
| UMAP | 把高维向量压成二维布局的方法；会损失信息 |
| PCA | 更简单、确定性的线性降维方法；本项目作为小数据或 UMAP 不可用时的兜底 |
| 余弦相似度 | 比较两个向量方向是否接近的分数 |
| BPM | 每分钟节拍数，描述速度，不等于整体活跃度 |
| dBFS | 数字音频相对满刻度的电平；不是人耳标准化响度 LUFS |
| ACT | 由速度、电平、打击比例和起音密度合成的声音活跃度工程分数 |
| BRI | 由频谱重心、滚降和高频比例合成的声音明亮度工程分数 |
| HPSS | 把音频近似分成持续谐波和瞬态打击成分的方法 |
| Chroma | 把频率归并到十二个音高类别的表示，用于调性估计 |
| M3U8 | 保存歌曲路径和顺序的 UTF-8 播放清单，不包含音频本体 |
| 内容指纹 | 当前使用文件 SHA-256；用来确认是不是同一份音频内容 |
| 幂等 | 同一写入请求重试多次，也不会产生重复结果 |
| DRM | 平台对受保护内容设置的数字版权管理；本项目不绕过 |
| Clean-room | 只参考公开行为、论文和文档，独立实现，不复制受许可证限制的源码 |

## 31. 交接人应保留的关键判断

1. 曲境真正的核心不是某个单独模型，而是“多来源证据 → 可视探索 → 用户审查 → 安全输出”的完整链条。
2. 可解释轴与高维相似度之间存在天然张力；当前混合布局选择了可读性优先、模型邻域有限补充。不要为了让图更像 UMAP 而失去 BPM/BRI 含义，也不要为了轴好看而声称二维就是完整听感。
3. 大模型能改善语言交互和解释，不能替代音频信号分析、歌词合法来源、流派数据库和用户确认。
4. 上云不是“把本机地址部署到服务器”。只要产品仍要读取用户任意本地音乐目录，本地代理或桌面封装就是架构的一部分。
5. 宁可保留“待确认”，也不要制造虚假精确度。曲境的长期竞争力来自用户信任，而不是标签数量。
